# ADR 0010: Offline-First Hybrid Sync Engine & Architectural Migration
# قرار التصميم رقم 0010: محرك المزامنة الهجين والمزامنة عند انقطاع الاتصال

## Status / الحالة
Accepted (Frozen) / مقبول ومثبت

---

## Context / السياق
كان النظام يعتمد تاريخياً على التخزين المحلي `LocalStorage` كمصدر أساسي للقراءة وتزامن بعض العمليات لخادم `Firestore` بشكل غير متزامن خلف الكواليس. مع توسع النظام وتعدد الفروع والمؤسسات، أدى بطء الاتصال أو انقطاعه في محطات أو فروع معينة إلى مخاطر فقدان المزامنة أو تأخر تسجيل الحركات المالية والمحاسبية.

تطبيقاً للمرحلة الخامسة (Phase 5: Architectural Migration) من خطة استقرار وتأسيس المنظومة (Stabilization Foundation)، تم نقل الموديولات المالية والحرجة تدريجياً وبنمط **Strangler Fig** إلى بنية هجينة تضمن الاعتمادية الكاملة ومزامنة البيانات في كل ظروف الاتصال.

---

## Decision / القرار المعماري
تطبيق نظام مزامنة هجين (Hybrid Synchronization Architecture) يعتمد المبادئ التالية:

1. **طابور التخزين الميداني (Offline Queue Engine)**:
   - إنشاء محرك `OfflineQueueEngine` وطابع العمليات المؤجلة `syncWriteWithOfflineFallback`.
   - عند محاولة الكتابة في `Firestore` وفي حال انقطاع الشبكة أو تجاوز مهلة الاستجابة (Timeout)، تُسجَّل العملية تلقائياً في طابور محلي آمن ومحمي (`offline_transactions_queue`).

2. **الاستمرار في العمل دون انقطاع (Zero Downtime)**:
   - يستمر المستخدم بالعمل وإجراء المعاملات المالية (المصروفات، السندات، قيود اليومية، التسلسلات) محلياً دون أي رسائل كراش أو تعطيل.
   - يعرض النظام مؤشراً حياً باللغتين العربية والإنجليزية (`OfflineSyncIndicator`) في شريط النظام العلوي لإشعار المستخدم بحالة الاتصال وعدد المعاملات المعلقة بانتظار المزامنة مع إمكانية المزامنة اليدوية ("مزامنة الآن").

3. **المزامنة والدمج اللحظي التلقائي (Auto-Flush & Mirroring)**:
   - بمجرد استعادة الاتصال بالإنترنت (`online` event)، يقوم النظام تلقائياً بتفريغ الطابور وإرسال البيانات المعلقة إلى Firestore.
   - تقوم مستمعات Firestore اللحظية (`onSnapshot`) بدمج المعاملات المسجلة أوفلاين مع البيانات القادمة من السيرفر وتحديث الـ LocalStorage تلقائياً كمرآة سريعة للقراءة الفورية (Instant Read Mirror).

---

## Migrated Critical Modules / الموديولات الحرجة التي تم تهجيرها
تم تطبيق هذا النمط تدريجياً دون أي هدم أو تعديل على الـ Schema على الموديولات التالية:
1. **المعاملات المالية (`transactions`)**: كتابة وقراءة متزامنة (`addTransaction`, `updateTransaction`).
2. **قيود اليومية المحاسبية (`journal_entries`)**: حفظ وتأكيد محرك المحاسبة المزدوجة (`AccountingBusinessEngine`).
3. **التسلسلات الرقمية للمؤسسات (`company_sequences`)**: توليد أرقام السندات والفواتير آلياً وضمان عدم تكرارها.
4. **المستخدمين والصلاحيات (`users`)**: حفظ ومزامنة بيانات المستخدمين والصلاحيات الميدانية.

---

## Justification & Pros / المبررات والإيجابيات
1. **حماية أصل البيانات المالية (Financial Data Integrity)**:
   - منع فقدان أو ضياع أي معاملة مالية أو سند صرف حتى في أسوأ ظروف الاتصال بالإنترنت.
2. **تجربة مستخدم سريعة وسلسة (Sub-millisecond UX)**:
   - القراءة تظل فورية ومباشرة من الـ Cache المحلي المرتبط بالـ Snapshot اللحظي، مما يضمن أداء ممتازا على جميع الأجهزة.
3. **شفافية حالة الشبكة (Transparent Status)**:
   - وضوح كامل للمستخدم بشأن حالة المعاملات غير المتزامنة من خلال شريط `OfflineSyncIndicator`.
4. **التوافقية الرجعية الكاملة (100% Backward Compatibility)**:
   - الصمود الكامل لجميع شاشات وواجهات المستخدم دون الحاجة لتغيير أي Component أو Props أو شروط عرض.

---

## Cons & Mitigations / العيوب وكيفية التعامل معها
- **إمكانية تعارض أرقام التسلسلات عند العمل أوفلاين على أكثر من جهاز بالتوازي**:
  - *الحل/المعالجة*: اعتماد آليات التوليد التكيفي وتحديث أرقام التسلسلات الذكي لكل شركة على حدة (`company_sequences`) لمنع التضارب.
